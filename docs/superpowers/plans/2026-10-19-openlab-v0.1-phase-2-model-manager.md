# OpenLab v0.1 — Phase 2 Hybrid Model Manager Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (\`- [ ]\`) syntax for tracking.

**Goal:** Turn the Phase-1 desktop shell into a safe local model laboratory with curated discovery, supported-file imports, hardware guidance, verified installations, and explicitly approved updates.

**Architecture:** Rust owns manifests, compatibility decisions, file transfers, installation transactions and SQLite state. React renders a curated catalogue and model lifecycle screens through scoped Tauri commands. Models are inert artifacts; they never become executable adapters through import alone.

**Tech Stack:** Phase-1 Tauri 2/React/TypeScript/Rust/SQLx stack; serde JSON, sha2, reqwest streaming, Tokio, Windows filesystem APIs and Vitest. Select compatible pinned library versions at execution time.

**Spec:** [OpenLab v0.1 foundation design](../specs/2026-10-18-openlab-v0.1-foundation-design.md)

**Prerequisite:** [Phase 1 desktop/supervisor plan](./2026-10-19-openlab-v0.1-phase-1-desktop-supervisor.md) completed and reviewed.

## Global Constraints

- Maintain one-model-at-a-time execution; installing a model is **not** permission to start additional inference.
- Model files reside in a configurable library outside source tree; user media and existing installed versions are never deleted as a side effect of update failure.
- An arbitrary Hugging Face URL or checkpoint is not automatically runnable. Accept only manifests and files supported by a registered, vetted adapter.
- Downloads and update checks require user initiation/approval, disclose source and license, and do not execute downloaded scripts or post-install hooks from model repositories.
- Include exact provider/repository/revision, artifact filenames, hashes or immutable-source verification, variant format, expected bytes, license, and adapter compatibility in every install record.
- Labels “Recommended”, “Possible with offloading”, “Untested”, “Unsupported” must be grounded; file size alone is not a VRAM estimate.
- Respect Tauri's restricted command and filesystem policy; never allow a web catalogue entry to specify arbitrary local executable paths.
- Follow task-level red/green/commit and maintain tests on Windows; never claim real model downloads or GPU generation unless exercised.

## Review Focus

1. **Filename \`../../AppData/evil.exe\` or a ZIP containing it:** Task 5 rejects traversal and symlink escape before writing outside staging.
2. **Connection interrupted after 60% with changed ETag:** Task 4 discards unsafe partial state and restarts verification, rather than appending incompatible bytes.
3. **Same logical model with different quantizations:** Tasks 1 and 6 distinguish variant versus weight release and never mark it a replacement update.
4. **Only model-card README changes upstream:** Task 6 reports metadata-only change, not a weight update.
5. **Insufficient space while applying update:** Task 5 leaves the currently installed revision ready to use and marks the candidate failed.

## Phase-2 completion gate

Curated models, supported imports, compatibility display, download/update progress, verification, rollback and persistence must be demonstrably functional. File corruption, unreviewed executable installs, or replacing a working model without approval block Phase 3. Installing a model is not proof of successful inference; that belongs to Phase 3.

## Execution handoff

Execute only after Phase-1 gate approval. Keep the plan and spec open during task reviews; do not broaden supported model families as an implicit part of this phase.
