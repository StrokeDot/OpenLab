# OpenLab v0.1 — Foundation Design Specification

**Date:** 2026-10-18  
**Repository:** StrokeDot/OpenLab  
**Status:** Approved by user on 2026-10-19 for implementation planning; implementation plan pending review  
**Target platform:** Windows 11 desktop, local-first  
**Design process:** Superpowers architectural design

## 1. Product intent and success criteria

OpenLab is a personal, local AI-model testing studio. It provides one clear interface for experimenting with open-source and other locally runnable, appropriately licensed AI models across **Image (OpenPixel)**, **Audio (Voice & Sound)**, and **Video (Motion)**. The application is a testing laboratory, not a replacement for production tools such as StrokeScribe or Voice Studio.

Its primary user wants to compare current and emerging model technology without rebuilding a user interface, navigating ComfyUI node graphs, or simultaneously loading large models. Initial reference hardware is a Windows 11 PC with approximately 16 GB GPU VRAM and 64 GB system RAM. These specifications are *target conditions*, not a promise that every model fits.

A successful v0.1:
- Opens as a real Windows desktop application with Image, Audio, and Video workspaces.
- Runs one verified local image-generation workflow through a supervised AI engine, without requiring the user to interact with its node graph.
- Uses one global execution lane: at most one local AI model/engine is actively loaded for generation at a time.
- Saves each image, the settings used, an exact model revision, and an inspectable comparison history.
- Manages a small curated model catalogue, model installations, version information, and safe user-approved updates.
- Recovers reasonably from an engine crash, a cancelled job, an interrupted download, or a restart.
- Does not silently execute unknown downloaded code or replace a working model.

## 2. Scope and exclusions

### Included in v0.1

1. Tauri 2 desktop host, Rust core, React + TypeScript frontend, and a consistent dark UI.
2. Three navigable workspaces: functional **Image/OpenPixel**; **Audio/Voice & Sound** and **Video/Motion** shells explicitly labeled as not yet integrated.
3. SQLite database for catalogue metadata, installations, settings, tasks, and generation results.
4. A Rust engine supervisor with one cross-workspace GPU execution lock and a FIFO generation queue.
5. Adapter interfaces for multiple engine types; one working image backend integration in this release.
6. Hybrid Model Manager: curated compatible model entries, import paths for supported models, download/install/update workflows, exact revision tracking, hardware assessment, and installation rollback.
7. Image prompt, supported model/variant, resolution, seed, progress, cancellation, result preview, save/export, and sequential comparison history.
8. Local logging, clear errors, startup recovery, Windows build/installer workflow, and automated tests.

### Explicitly excluded in v0.1

- Working voice cloning, audio synthesis, voice conversion, music generation, or video generation.
- Multiple simultaneous AI jobs, multi-GPU scheduling, distributed/cloud compute, commercial model hosting, or accounts.
- Automatic support for arbitrary Hugging Face models or execution of arbitrary imported scripts.
- An open-ended workflow/node editor, full ComfyUI UI embedding, and advanced image editing modes.
- Automatic app self-updating and unattended model replacement.
- Claiming benchmark equivalence just because two model families receive the same seed or step count.

These are future extensions, not hidden requirements of the foundation milestone.

## 3. Architecture and responsibility boundaries

### Desktop user interface — Tauri 2 + React + TypeScript

Responsibilities: navigation, forms, model catalogue views, downloads, progress, result preview, history and comparison, and user consent. The frontend communicates through narrow typed Tauri commands/events. It does **not** launch arbitrary commands, write directly to privileged model folders, or talk to untrusted local services.

### Application core — Rust

Responsibilities:
- Own the SQLite database, migrations, configuration, task state, and durable job records.
- Supervise allowed engine processes and their process trees, resolve executable paths, and handle shutdown/restart.
- Hold a single global execution reservation from preparation through model unload/engine exit.
- Control download and verification pipelines, model installation records, and update transactions.
- Enforce safe paths and permission boundaries, keep records of exact source revisions, and report events to the frontend.

Rust is a supervisor and coordinator; it does not reimplement the inference models.

### Engine adapter boundary

A versioned, typed adapter contract defines:
- **describe**: engine identity, installed version, supported operation kinds, model formats, and input/output schema.
- **probe**: dependencies, executable/sidecar availability, local health, backend capabilities.
- **start / health / stop**: managed lifecycle with bounded timeouts and process-tree cleanup.
- **prepare_model / generate / cancel / unload**: one task's model and inference operations, with progress events.
- **diagnostics**: sanitized diagnostic detail and actionable failure codes.

Adapters normalize engine-specific differences into a shared result: job ID, output paths, metrics when actually measured, warnings, and traceable model revision. Capabilities are discovered per adapter/model and unsupported controls are hidden or disabled rather than silently ignored.

**Target adapters:**
- **ComfyUI HTTP/WebSocket adapter:** first real image inference path. Runs a bundled/installed vetted workflow headlessly through the API; the user never has to see nodes. Probe validates custom-node/workflow compatibility. Restrict networking to loopback and authenticate/limit local control where feasible; do not expose a public listener.
- **Python/Diffusers adapter:** interface and probe shape prepared for later implementation, without committing v0.1 to shipping multiple complete inference stacks.
- **Future external adapters:** follow the same contract and isolation rules; importing a model alone does not create an adapter.

V0.1 integrates one actual image model. **FLUX.2 klein 4B** is the preferred first candidate, but the implementation must independently confirm appropriate license, workflow files, runtime dependencies, disk requirements, and successful generation on the target Windows system. If this candidate cannot pass, the replacement model requires an explicit design change/review rather than quietly expanding scope or claiming success.

## 4. Execution state machine and the one-model rule

A job transitions through:

**queued → preparing → running → unloading → succeeded**, or into **cancelled** / **failed** after cleanup. Jobs are persisted with timestamps, requested model identity/revision, status, output information, and error detail.

Rules:
- A single Rust scheduler owns one global permit. Only one job may be preparing, generating, or cleaning up at once, across all workspaces.
- FIFO order applies to normal queued requests; cancelling a queued request removes it without touching the current engine.
- The permit remains held until the old model is demonstrably unloaded or the managed engine process has exited. A UI state change alone is not sufficient.
- Switching models first unloads the active model or shuts down its engine; the next model starts only after cleanup succeeds.
- Cancellation is requested cooperatively first; after a bounded grace period the supervisor terminates the owned process tree and verifies it has exited. Never kill unrelated user processes.
- On an engine crash, mark the job failed, save partial diagnostics, release locks only after process cleanup, and offer a safe restart. On application startup, persisted in-flight jobs become **interrupted** and are not automatically re-executed.
- Output is written to a temporary job directory and published into history only after validation. Failed runs cannot masquerade as successful results.

An adapter can report that VRAM is still reserved; the supervisor may stop the entire owned engine before proceeding. GPU monitoring is advisory; process lifecycle and serialized scheduling enforce the rule.

## 5. Model Manager: hybrid catalogue and safe lifecycle

### Catalogue and import

The app ships a small curated set of **compatibility manifests** instead of pretending to execute every model shown on the internet. A manifest contains:

- Unique catalogue ID, publisher, display name, modality, operations and model family.
- Source URL/repository, immutable revision/commit where available, file list and hashes where available.
- Weights variant/quantization/precision and total required download bytes.
- Supported adapter and required workflow/engine compatibility constraints.
- License name, source link, commercial-use caveats where stated, and explicit user-acceptance requirements.
- Hardware guidance: VRAM/RAM/disk requirements, offloading support, and known limitations.

Users can browse curated models and **import an existing supported checkpoint or manifest** from local storage. Import validates format and registered adapter compatibility and never executes arbitrary code found alongside the model. Unsupported files remain clearly marked **not runnable**. A future opt-in adapter ecosystem can expand supported formats.

### Compatibility labels

- **Recommended:** supported adapter and tested/validated configuration for relevant hardware.
- **Possible with offloading:** supported but may be substantially slower; explain memory assumptions.
- **Untested:** metadata insufficient or not benchmarked on this configuration.
- **Unsupported:** required backend or minimum verified resources unavailable.

Hardware detection uses real free disk capacity and system capabilities; do not equate file size with full runtime memory usage. Allow the user to see the basis of a compatibility recommendation, and never promise a model will run from VRAM figures alone.

### Download and installation

1. Preview exact source, revision, file sizes, license, disk requirement, and dependencies before a user-approved download.
2. Use a user-configurable model library outside the application source tree. Application metadata lives in an app-specific data directory.
3. Download into a staging directory; support resumable HTTP-range downloads only when server identity and content metadata permit safe continuation.
4. Verify digest/size or immutable upstream revision as applicable. Fail closed on mismatches, incomplete manifests, unsafe file paths, path traversal, or symlink escape.
5. Keep any engine code/dependency installation as an explicit, vetted adapter-specific process; downloading weights never executes scripts.
6. Atomically publish a verified installation and record its exact revision and variant. On a failed installation, keep old installations untouched and offer retry/cleanup.

### Update meanings

The UI separately identifies:
- **Weight revision:** changed model weights within the same repository/release.
- **New model release:** a separately named successor/family version.
- **Additional variant:** new quantization or precision for an existing release.
- **Metadata-only change:** documentation or catalogue information changed; no inference weights changed.

Update checks may access approved publisher/catalogue endpoints when initiated by the user. **No unattended updates and no automatic replacement**. The user approves the exact proposed change, and the currently working installation remains available until the replacement passes verification. Previous results continue to point to their original model revision even after an update.

## 6. Main user experience

The Windows window uses a simple dark interface and avoids ComfyUI's workflow graph:

- **Left navigation:** Image / OpenPixel, Audio / Voice & Sound, Video / Motion, Model Manager, History, Settings/Diagnostics.
- **Image workspace:** choose installed model and supported version/variant; enter text prompt; select available size, seed and adapter-supported options; Generate / Cancel; preview and save output; see errors/logs only when needed.
- **Audio and Video workspaces:** visually complete shells with clear nonfunctional-state notices rather than fake Generate actions.
- **Model Manager:** Installed, Discover, Updates, Downloads, and model Details (source, version, variants, license, compatibility, engine needs).
- **History/comparison:** choose previous runs; display outputs side-by-side and metadata in a consistent panel, without rerunning anything.
- **System status:** concise display of current engine, active job, CPU/RAM/VRAM metrics when available, and queue state.

Selected settings persist locally. Unsupported controls must be explained rather than accepting input that will be ignored. Download, install, and update controls have real progress, cancellation semantics, and actionable error feedback. Keep controls usable at typical 1440p resolution and at smaller laptop window sizes.

## 7. Local data model and reproducibility

Use SQLite with versioned migrations and a separate on-disk results/model library. Logical entities:

- **model_catalogue**: stable logical model ID, provider, release, capabilities, manifest revision and licensing references.
- **model_variant**: variant ID, precision/quantization, artifact references, size and resource expectations.
- **model_installation**: exact installed artifact revision, verified path, state, timestamps, adapter version, and verification details.
- **engine_installation**: engine/adapter identity, install path, version and health state.
- **job**: request, workspace, model/variant revision, lifecycle timestamps, seed, normalized input, settings, status and error code.
- **result**: job reference, local media path, output metadata, generation duration, optional measured resource peaks, user notes and comparison group.
- **settings**: configurable model root, results root, logging/privacy preferences, and UI preferences.

Store large media and checkpoint files outside SQLite. Generated results must retain enough immutable provenance to identify the engine/workflow/model revision that produced them. If the original model is removed later, history stays browseable and is marked not directly reproducible until that revision is restored.

Do not persist a fake peak-VRAM reading when measurement is unavailable. Never delete user results as part of model cache cleanup. Use atomic writes, backups/migration checks, and safe recovery if migration fails.

## 8. Security, privacy and reliability boundaries

- **Local-first:** prompts, references, and outputs remain on the local machine. The app only contacts external endpoints for explicitly initiated model discovery, update checks, and downloads. No cloud inference in v0.1.
- Do not expose general-purpose shell execution or unrestricted arbitrary file paths through the Tauri frontend. Use narrow permission-scoped commands.
- Only launch vetted adapter executables from recorded, controlled locations. Protect subprocess environment variables and sensitive values in logs.
- Keep ComfyUI/Python services bound to loopback; restrict or authenticate their control endpoints when supported. Avoid exposing them to the LAN and block requests targeting arbitrary network addresses.
- Enforce outbound download source policy, timeout, size limits, integrity verification and safe extraction. Never implicitly install executable code from a model import.
- Model licensing is recorded and surfaced; **open weights do not necessarily mean unrestricted commercial use**.
- Sanitize logs and errors; avoid copying the user's full prompts or private filenames into externally shareable diagnostic bundles without consent.
- On restart, reconcile missing model files, incomplete downloads and interrupted jobs without deleting completed user output.

## 9. Errors and recovery behavior

| Condition | Expected behavior |
| --- | --- |
| Model too large or dependencies missing | Show concrete compatibility reason and supported alternatives; do not start inference. |
| Download interrupted | Preserve staged file only when safe; offer resume or verified retry; previous install unaffected. |
| Hash mismatch or invalid path | Reject candidate; retain installed version and explain the failure. |
| Engine fails to start | Surface version/dependency error; stop owned partial process tree; allow retry. |
| Generation cancelled | Cooperate, then controlled process-tree termination if needed; no false-success result. |
| Engine crash during generation | Mark failed/interrupted, preserve safe diagnostics, and release GPU reservation only after cleanup. |
| Application closes/restarts mid-job | Reconcile recorded state on next launch; never silently resubmit a generation. |
| Database migration error | Preserve existing database, show recovery action and do not proceed with destructive writes. |

## 10. Verification and acceptance

### Automated tests

- Rust scheduler state-machine tests: never grants two active jobs; FIFO; queued and active cancellation; model switch cleanup; crashing engine; stale job recovery.
- Adapter-contract tests against a fake local engine for start, progress, result, timeouts, cancellation and diagnostics.
- Model catalogue/manifest schema and compatibility tests, including unknown formats, incorrect hashes and incomplete metadata.
- Download/install tests for partial downloads, retry, path traversal/symlink escape, corruption, update rollback and original installation preservation.
- SQLite migration and persistence tests, including restart after interrupted jobs and history retained if model weights are removed.
- React/TypeScript UI tests for navigation, model selectors, nonfunctional Audio/Video shells, state labels and disabled incompatible actions.
- CI: formatting, type checking, unit/integration suites, and Windows packaging/build checks. A passing CI build is **not** evidence that GPU inference works.

### Manual Windows hardware acceptance

On the target Windows PC:
1. Install and launch a built package without development tooling; verify the three workspaces and local storage directories.
2. Install the vetted image model/engine through the manager and prove correct file checks and a clear final installed state.
3. Generate an actual image from a prompt, record output/seed/revision, and open the saved file after application restart.
4. Run another generation sequentially (including a model switch if two models have been installed) and verify no overlapping owned inference processes.
5. Cancel a generation and an interrupted download; prove there is no incorrectly published output or broken prior installation.
6. Induce an owned-engine failure safely and verify error reporting, cleanup and a successful subsequent retry.
7. Compare two saved outputs without starting new inference, and confirm history metadata is still present after app restart.
8. Test update detection and user refusal; verify rejecting an update makes no change to a working model.

**Release gate:** No v0.1 acceptance claim until both automated checks and one real GPU end-to-end image-generation pass are evidenced. If the preferred FLUX.2 klein 4B cannot be supported on target hardware, pause for model substitution approval.

## 12. Deliberate design trade-offs

- **Rust-supervised adapters over a Python-only supervisor:** better OS/process ownership and a durable single-job boundary, at the cost of more initial integration work.
- **Hybrid catalogue over unrestricted repository search:** predictable supported installations and safe imports, at the cost of fewer immediately runnable models.
- **One supported image pipeline in v0.1 over three functional media pipelines:** proves the architecture on actual hardware before adding complicated speech/video dependencies.
- **Sequential generation over parallel model loading:** better predictability on 16 GB VRAM and simpler recovery, at the cost of total throughput.
- **Explicit updates with old-version retention over automatic replacement:** protects working installations and reproducible tests, at the cost of extra disk space and user decisions.

The final intention is a dependable local testing studio: simple to operate, honest about compatibility, and extendable without requiring a new UI for every model.
